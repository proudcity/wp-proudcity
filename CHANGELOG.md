## 2026-08-27

- Added `^node$` to `www/bots.csv` after a sitemap scrape took `prod/montgomeryoh` fully offline. All four pods were `OOMKilled` (exit 137) against the 800Mi limit; over a 10-minute sample, 3852 of 3994 requests to the tenant (96%) came from user agent `node` and every one targeted a Yoast sitemap — `/sitemap.xml`, `/sitemap_index.xml`, `/attachment-sitemap*.xml` and ~15 others — peaking at ~1000 req/min. Yoast regenerates each sitemap per request, so at that rate the Apache workers blew past the cgroup limit with the HPA already pinned at its max of 4 replicas and CPU at 932% of the 80% target. It self-amplified, since the resulting 502s made the client retry. `node` is the bare UA of Node's built-in `fetch`, which is undici — we already blocked `undici`, so this was the sibling entry we had missed, alongside the existing `ultimate_sitemap_parser`.

Every other entry in the file is a distinctive product name, but `bin/entrypoint.sh` compiles each line into `RewriteCond %{HTTP_USER_AGENT} <line> [NC,OR]`, which is unanchored substring matching — a bare `node` would also catch NodePing and other uptime monitors that cities run against their own sites. Verified the generated rule renders as `RewriteCond %{HTTP_USER_AGENT} ^node$ [NC]` (correctly picking up the trailing-OR strip as the last entry) and that `node` matches while `node-fetch/2.6.7`, `NodePing` and `Nodemailer/6.9` do not.

Our own Node services do not send it either — `proudcity-api-swagger`, `proudcity-city-api` and `proudcity-elastic-docs-api` all use the `request` library, which sends no User-Agent by default, and they only read `req.headers['user-agent']` rather than setting it outbound. Deployed as `master-4f13184bb765a039c97d42c513946c3f83d0469f`; `node` traffic fell to a single 403'd request in the following three minutes, CPU went 932% → 51%, memory 640–744Mi → 342Mi, and the HPA came off its max back down to 2 replicas.
- Fixed `prod/rutherfordtonnc` being consistently slower than its peers, which turned out to be CPU throttling rather than anything about the site. It was the only WordPress deployment in `prod` with a restrictive CPU **limit**, set to `150m` — equal to its `requests.cpu`. Of 104 prod WP deployments, 100 have no CPU limit at all and the other three sit at 2500m–3400m. A CPU limit is a hard kernel-enforced ceiling, so the container froze once it spent its quota for each 100ms window regardless of how idle the node was: `cpu.max` read `15000 100000`, and one pod showed 5480 of 7162 periods throttled (76.5%) with 573s frozen against 87s running. Measured across a single homepage request, 0.56s of real CPU work stretched to a 3.13s TTFB with 2.73s of that spent frozen — at ~97 requests per 30 minutes, so it throttled on a single visitor. Removed the limit with `kubectl patch`, leaving `requests.cpu` at 150m; `cpu.max` now reads `max 100000` with `nr_throttled` and `throttled_usec` both at 0.
- Deactivated Query Monitor on `prod/rutherfordtonnc`, which was active in production and the only prod site running it (`WORDPRESSORG_PLUGINS=query-monitor`). It instruments every query, hook and HTTP call and holds them in memory for the whole request, so it taxed both CPU and memory on every page load and was likely a contributor to that site's `OOMKilled` restarts as well. Deactivation persists across restarts because activation state lives in the database and `bin/entrypoint.sh` only downloads `WORDPRESSORG_PLUGINS` without activating them, though the files are still re-fetched from wordpress.org at boot until the entry is dropped from the deployment env var. Combined effect of both fixes on TTFB: 8.1–12.9s before, 2.0–3.6s after the plugin came off, ~0.52–0.58s after the CPU limit was removed, against 0.18s for peer `cliftonheightspa`.
- Ruled out the obvious suspects on rutherfordtonnc before landing on the limit: the database is healthy and small (1,548 posts, largest table `wp_postmeta` at 9.4MB, autoload 0.27MB across 1,104 options), 51 active plugins is in line with peers (bedfordoh 50, cliftonheightspa 50, carnationwa 53), Redis is connected with a valid drop-in and no errors, traffic is trivial, and the 800Mi memory limit is the fleet norm at 71 of 104 sites. Also audited the three remaining CPU-limited sites and none need action — `petalumaca`, `sanrafaelca` and `santaanaca` throttle at 0.014%–0.265% of periods across 8 pods, three orders of magnitude below rutherfordtonnc. All three set the limit well above the request (3.3×–6.3×), which is the distinction that matters: a limit equal to the request turns a burst ceiling into a permanent cap at the scheduling floor.

## 2026-08-26

- Added version pinning to `bin/entrypoint.sh` for `WORDPRESS_PLUGINS` and `WORDPRESS_THEMES`. Both lists were installed with a bare `git clone -- "$s"`, which takes default-branch HEAD, so every pod start re-cloned whatever upstream had last pushed. Any restart — a deploy, a node drain, an OOM kill, an autoscale event — silently upgraded every git-installed plugin on that site, with no deploy on our side. Roughly 30 repos are wired up this way across `prod` and `test`; the ones we do not control (`FileToWeb/filetoweb-integration`, `FileToWeb/filetoweb-forms`, `katzwebservices/Gravity-Forms-Constant-Contact-Add-on`, `Automattic/batcache`) were the real exposure. An entry may now append `#<tag-or-branch>` to pin it, e.g. `git@github.com:FileToWeb/filetoweb-integration.git#0.1.48`. Entries without `#` are unchanged and still track HEAD, so this ships safely ahead of any deployment edit. Both loops now call a shared `clone_repo_entry()` helper rather than duplicating the logic.
- A pin that cannot be resolved leaves the repo **uninstalled** and logs a warning, rather than falling back to HEAD — silently installing an unintended version is the exact failure the pin exists to prevent. New options are placed ahead of `--` so the repo URL still cannot be read as an option, preserving the argument-injection hardening from `ca548bc` (CVE-2018-17456). Pinned clones use `--depth 1`, so they are faster than the previous behavior rather than slower, and set `advice.detachedHead=false` because a pinned clone always lands detached and git's advice block is otherwise a page of noise per plugin in the pod logs.
- Verified against the live `FileToWeb/filetoweb-integration` repo: `#0.1.46` installs 0.1.46, an unpinned entry installs 0.1.48 (current HEAD), a nonexistent ref installs nothing and warns, and an empty entry is skipped. Note `git clone --branch` accepts a tag or a branch but not a raw commit SHA; both FileToWeb repos tag every release, so tags are the pin.
- Prompted by pc-dev-issues#374, where an upstream release of `filetoweb-integration` shipped a migration whose `meta_query` generated a five-way `wp_postmeta` self-join (~434M intermediate rows on the affected tenant) and never converged, taking a production site fully offline. That release reached our sites on their next pod restart, and mid-incident a `kubectl rollout restart` pulled a further upstream release that invalidated the mitigation which had just been applied. Reported upstream as FileToWeb/filetoweb-integration#20.

- Added `www/wp-content/mu-plugins/loopback-basic-auth.php`. Sites gated by the `AUTH_REQUIRED` env var answer every unauthenticated request with a 401, including WordPress's own loopback requests — `wp-proud-core`'s `ProudAuthentication::checkAuthentication()` exempts CLI but not the HTTP request the CLI process makes back to Apache. That is why `release-2026.08.18.1821.sh` bailed on beta with `loopback to admin-ajax.php returned '401'`: the WP-Stateless background processor dispatches its batches via `wp_remote_post()` to `admin-ajax.php`, and the wall 401s it. No CLI exemption, deliberately: the loopback we need to fix originates under WP-CLI. Verified on beta — loopback went 401 to 200, credentials confirmed not attached to `http://`, to an alternate port, to other same-host paths, to `beta.proudcity.com.evil.test`, or to external hosts.

## 2026-06-25

- Added an Apache `[F]` guard in `www/.htaccess` (ships to `/app/wordpress/.htaccess`) to short-circuit backdoor/webshell scanner probes for non-existent root-level script paths (e.g. `/asdf.php`, `/root.php`, `/xll.asp`, `/shell.php5`). These probes were falling through the WordPress rewrite to `index.php`, triggering a full WP bootstrap and ~80–96 KB themed 404 render per request, burning PHP/Apache workers, CPU, and memory fleet-wide. The load was driving OOMKills and repeated up/down flapping on the kalamazoomi (ktwp.org) tenant in the prod namespace (CPU pinned at 306%, HPA at MAXPODS=4, memory OOMKilling at the 800 Mi cap). The rule (`RewriteRule ^[^/]+\.(php|phtml|php[0-9]?|asp|aspx|jsp|cgi|pl)$ - [F,L]` behind a `RewriteCond %{REQUEST_FILENAME} !-f` guard) returns a cheap 403 (239 bytes, no PHP) for non-existent root-level script paths. The `!-f` condition exempts real on-disk WP entry points (index.php, wp-login.php, wp-cron.php, xmlrpc.php, etc.); the `^[^/]+\.` root anchor prevents it from ever matching `/wp-admin/*.php` or `/wp-includes/*.php`. The rule is placed in the existing top-of-file hardening zone above the WP catch-all, alongside the UA-block rules. **The rule must live in `.htaccess`, not the vhost `<Directory>` block**: `/app/wordpress/.htaccess` declares its own `RewriteEngine On` context, which overrides the vhost rewrite rules (they are not merged/inherited), so a vhost-placed rule never fires for doc-root requests. This was verified on beta — the initial vhost placement (commit `fdb4b43`) left probes getting the full 96 KB WP 404; moving the rule to `.htaccess` (commit `083ce92`) dropped probes to 403 (239 bytes) with no PHP invoked. Post-rollout: CPU fell to ~19%, memory stabilized ~450 Mi, HPA scaled back to MIN 2, no further OOM events on ktwp.org. (commits `fdb4b43`, `083ce92`)

A generic `User-agent: *` block covers Googlebot and any other compliant crawler; named blocks for Applebot, Bingbot, YandexBot, and DuckDuckBot add `Crawl-delay: 10` plus the same path list.
